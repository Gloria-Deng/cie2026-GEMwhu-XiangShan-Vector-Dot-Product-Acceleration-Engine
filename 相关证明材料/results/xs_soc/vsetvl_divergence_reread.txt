=== 2. 按真实列序重读那条原始读数 ===
（下面两行从 vsetvl_divergence_linux.txt 第 3 节原样搬来，一个字没改）
  vl    different at pc=..., right = 0x0000000000000000, wrong = 0x...0010   (16)
  vtype different at pc=..., right = 0x8000000000000000, wrong = 0x...00c0   (0xC0 = e8/m1/ta/ma)
reading: 参考机 = {vl 0, vtype 0x8000000000000000}；被测（这份 RTL）= {vl 16, vtype 0xC0}
why_this_settles_it: `0xC0` 是 `vsetvli …, e8, m1, ta, ma` 的**请求值**，只有真把这条指令执行
          进去的一侧才可能给出它；`{vl 0, vtype 0x8000000000000000}` 正是这两个 CSR 的
          **复位值**。原始读数里持请求值的一侧是 `wrong` 列 ⇒ 被测（这份 RTL）；持复位值的一侧
          是 `right` 列 ⇒ 参考机。**「这份 RTL 的 `vsetvl` 没生效」这句被它自己引的原始读数否掉。**
consistency: 同一份归档还记「probeN / probeP / probeS 三者一致」——三条探针的差别只在编码写法
          上，被测侧三次都给出请求值、参考机侧三次都给出复位值，与上面的读法一致。

=== 3. 参考机为什么停在复位值：一行根因 ===
mechanism: 参考机的导出不是「每问一次就读一次 NEMU 的 CSR」，而是「一份镜像 + 一个脏位」：
  priv.c:2134        static void csr_write(uint32_t csrid, word_t src) {
                       word_t *dest = csr_decode(csrid);
                       IFDEF(CONFIG_SHARE, csr_difftest_mark_dirty());   ← 真 CSR 写都标脏
  vcommon.c:112-129  void set_vtype_vl(Decode *s, int mode) {
                       …
                       vtype->val = id_src2->val;   vl->val = vl_num;    ← 直写，不走 csr_write
                       rtl_sr(s, id_dest->reg, &vl->val, 8);
                       vstart->val = 0;                                  ← 直写
                     }
  vp.c:39            void vp_set_dirty() { mstatus->vs = EXT_CONTEXT_DIRTY; … }  ← 也直写 mstatus->vs
  isa/riscv64/difftest/ref.c:135-139
                     static inline void csr_prepare_if_dirty() {
                       if (csr_difftest_dirty) csr_prepare();
                     }
  isa/riscv64/difftest/ref.c:132   `csr_prepare()` 结尾自己就调 `csr_difftest_mark_clean()`
          （v1 曾把这两处写成 ref.c:135-137 与 :131，行号偏了一位：131 是
          `csr_prepare()` 尾上的 `#endif`，`csr_difftest_mark_clean();` 在 132；
          `csr_prepare_if_dirty()` 的函数体到 139 行的 `}`。已核正确的引文：
          priv.c:2134、priv.c:2136/3663/3733、csr.h:2080、vcommon.c:112-129、vp.c:39、
          ref.c:47-55、ref.c:57-86。）
consequence: `vsetvli` / `vsetivli` 走完全程都没把脏位立起来 ⇒ 参考机→被测那一支的
          `csr_prepare_if_dirty()` 是空操作 ⇒ 导出的 `vl` / `vtype` / `vstart` 停在上次刷新
          （那条语料里就是复位值），而被测这两列是真的。**这不是这份 RTL 的问题，是参考机导出
          面的问题。**
prediction_it_makes: 这条机制预言了两件事，归档里的原始读数两件都中：
          (a) 不同的列恰是 `vl` 与 `vtype` 两列（`vstart` 本来就是 0；那条探针没动别的 CSR）；
          (b) `right` 列正好是这两个 CSR 的**复位值** `{0, 0x8000000000000000}`。
why_mstatus_VS_was_fine: 同一个探针里 `mstatus.VS` 读回去是对的——它那一格是 `csrs mstatus, x10`
          写进去的，走的是 `csr_write()`，标脏了。这一格反而是本机制的正对照。
